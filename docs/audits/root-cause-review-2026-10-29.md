## 1. P1：工作树状态读取失败被当作无改动，参与强制删除

位置：`server/worktree-service.ts:130`、`:491`、`:515`。

`getUncommittedCount()` 在 Git status 超时或报错时返回 `{isDirty:false,count:0}`。`finalizeSubagentWorktree()` 把这个值用于判断是否自动清理；HEAD 与 base 相同且存在未提交工作时，只要 status 查询失败，就可能进入 `removeWorktree(..., true)`，随后删除分支。HEAD 查询异常同样降级成 ahead=0。

根因：展示用的“最好努力”读取结果，被复用于破坏性操作的授权依据，未知状态被压成安全状态。

根治：状态采用 clean / dirty / unknown 三态；仅所有检查明确成功且无改动时允许自动删除。失败应保留工作树并报告原因，不能将增加超时或重试当作安全边界。

## 2. P1：插件 cron 到期后重新查询未来时间，跳过本次执行

位置：`server/plugins.ts:4997`、`server/plugin-schedule.ts:141`。

`armCron()` 捕获 next 设置计时器，回调却重新调用 `nextCronFire(parts, Date.now())`。该函数从下一分钟开始搜索，因此正常到期时得到的是下一次，而非本次，`at <= now + 1000` 不成立。分片计时解决了长延迟溢出，却丢失了本次 dueAt 身份。

定向复现：直接调用当前源码的 `parseCronSpec` / `nextCronFire`，每分钟任务计划 10:01，回调在 10:01 重新得到 10:02，`willFire=false`。这是到期判断表达式的确定性复现，未启动真实插件或计时器。

根治：保存本次 dueAt，分片醒来比较 now 与这个 dueAt；到期执行后才计算下一次，补跑与时钟跳变纳入同一状态转换。

## 3. P1：删除运行中的画布不终止执行，异步收尾会复活工程

位置：`server/canvas/canvas-dispatch.ts:79`、`canvas-agent-tool.ts:384`、`canvas-store.ts:239`、`canvas-orchestrator.ts:537`。

两个删除入口仅删除图文件。节点完成仍调用运行态保存，而保存函数发现文件不存在会写回完整旧图；之后仍处理下游边。结果是工程重新出现，删除后仍可能调用模型或启动下游操作。

根因：删除持久文件没有使运行身份失效；运行态更新兼任创建。

根治：删除先撤销图运行代次并取消执行，再删除文件；所有完成回调、写盘和下游派发校验代次。运行态保存只允许更新现存工程。单独加 stopAll 不能挡住跨 await 返回的旧回调。

## 4. P1：插件设置落盘失败仍发布运行态并回报成功

位置：`server/plugins.ts:1757`、`:1783`、`:1985`、`server/dispatch-plugin-handlers.ts:74`。

普通设置写入失败只记日志，仍返回 clean。调用方触发 settingsHandlers 并走成功回执，导致内存新配置与磁盘旧配置分裂。secret 还在逐字段校验过程中写入，后续字段校验失败可能留下部分提交。

根治：完整校验、暂存、持久提交、发布运行态形成明确边界；失败向上返回。secret 与普通配置需要共同提交或可恢复事务，禁止校验循环中产生持久副作用。

## 5. P1：MCP 改名或迁移作用域先删后写，失败丢配置

位置：`server/mcp-manager.ts:85`、`:189`、`:223`。

改名或迁移先删除旧记录并写回，再写新记录。第二步失败或进程退出后，旧配置已经丢失。同文件改名也拆成两次写入；直接覆盖正式文件及读取错误降级空配置进一步扩大风险。

根治：同文件改名一次内存变换后原子提交；跨文件迁移先持久保证目标存在，再移除源，配可恢复迁移状态。读取明确区分不存在、损坏和不可读，后两者禁止覆盖写回。

## 6. P1：DSH 切项目仅改宿主 cwd，重启引擎仍在旧目录

位置：`server/dsh/dsh-agent-service.ts:5807`、`server/dsh/dsh-client.ts:150`、`:314`、`:792`。

切 A 到 B 更新服务 cwd 后对原 runtime 调用 restart。restart 只更新模型/provider，初始化仍使用构造时保存的 A cwd。UI 和文件树显示 B，模型相对路径操作却仍可能落在 A。

根治：工作区变更使用目标 cwd 创建并初始化新 runtime，成功后提交切换；不能用只重启进程代替运行时身份迁移。

## 7. P1：Universal 旧回合找不到归属后回退 active，串写新项目

位置：`server/universal/universal-session.ts:948`、`:1013`、`:1786`。

回合结束通过 turnConvId 找归属，失败则回退 activeConv。切项目直接清空 conversations 且不等待旧回合终止。旧回合完成后找不到原会话，于是将回复、工具结果和统计追加到新项目当前会话，并按当前 cwd 保存。

根因：补了 ID 锚定，但仍让可变全局 active/cwd 充当异步归属的兜底。

根治：每回合捕获稳定会话对象、cwd、driver 与运行代次，贯穿所有回调和保存；归属失效禁止回退 active。切项目应取消并等待完成，或让旧运行时独立收尾。

## 8. P1：Claude 与 Durable 共用历史目录，底层会话 ID 跨引擎恢复

位置：`server/index.ts:1814`、`:1828`、`server/universal/session-store.ts:19`、`universal-session.ts:820`、`drivers/claude-code.ts:280`。

两个服务使用同一 dataDir，历史仓库仅按 cwd 与 conversation ID 区分。切换引擎后可直接加载另一引擎的记录，将 driverSessionId 传给当前驱动恢复。Durable ID 可作为 Claude resume 参数；反向恢复可能走目标查找失败/root 回退，两者还可能覆盖同一历史文件。

根治：存储键加入 engine，记录并校验 driverKind；跨引擎导入只能转换消息并新建底层会话，不复用 driverSessionId；已有数据需迁移或隔离。

## 9. P1：子代理创建没有贯穿父工具取消，停止后仍可启动

位置：`server/subagents.ts:553`、`server/agent-service.ts:1296`、`:1461`。

spawn 工具收到 signal 但未传入创建链。等待 runtime、扩展绑定或模型恢复时父对话停止/关闭，创建恢复后仍可注册并投递 prompt。关闭时尚未登记的后代不能被后代枚举清理。

根治：取消信号与稳定父 runtime 身份贯穿创建；注册和首次投递前校验有效性，失败统一回收未提交资源。

## 10. P1：同一对话可并发强制重建，后完成结果覆盖前者

位置：`server/agent-service.ts:10822`、`:10879`、`:10930`、`:10941`。

重复停止产生独立超时器及局部 forced 标记，两条强制重建链可以同时创建 runtime。提交仅检查对话仍存在，依次覆盖 conv.runtime/session，可能遗留被覆盖 runtime，或替换已经接受新消息的实例。

根治：每对话单一 interrupt/reset promise；提交绑定原 runtime 代次，失去提交资格的候选实例必须销毁。

## 11. P2：审批过户重编号后，原 AbortSignal 回调失效

位置：`server/agent-service.ts:6302`、`:11682`、`:11817`。

取消回调捕获旧审批 id。过户重新分配 id 并迁移条目后，取消仍删除旧 id，失败直接返回，不结算 Promise，不清理目标审批；旧 id 碰撞其他条目时还有误删风险。

根治：用稳定请求对象作为结算身份，展示 id 和持有方可迁移；取消、答复、销毁共用一次性 settle，删除当前持有方的当前条目。

## 12. P1：目标设置等待清理后借用新代次，旧请求无法可靠作废

位置：`server/goal-service.ts:691`、`:696`、`:749`、`:1383`；并发入口 `server/dispatch-domain-handlers.ts:502`。

设置目标 A 递增代次后等待 stopDelegated；期间清除目标或设置 B 再次递增代次。A 恢复不校验原代次，继续写状态，启动时重新读取最新 generation，使旧请求借用新代次通过守卫。

根治：入口捕获操作代次，等待后及每次写状态、抢占或派发前核验；设置、清除、关闭共用目标转换边界，只允许最新有效操作提交。

## 13. P1：DNS 校验未绑定实际连接，不能保证防住 DNS rebinding

位置：`server/net-guard.ts:216`、`:262`、`:285`；重复路径 `server/preset-share.ts:686`、`:707`；市场调用 `server/market-service.ts:189`。

resolveAndValidateUrl 返回已验证 IP，但实际 fetch 仍以原域名发起连接，未使用这些 IP。受控域名在预检查时返回公网 IP，实际连接解析时返回内网 IP，仍可能访问内网。逐跳 URL/DNS 校验并没有关闭检查与使用之间的窗口。此项基于传输调用链核实，未运行 DNS 攻击复现。

根治：统一受控 HTTP 传输，为每次连接使用已校验且固定的地址，保留原 Host/TLS servername；重定向逐跳重新验证并绑定连接，preset 与市场复用同一设施。

## 整改顺序与验收

1. 首先处理误删工作树、错误工作区执行与跨项目串写，以及停止/删除后继续执行。
2. 再修复调度到期语义、配置提交与引擎历史隔离。
3. 收口审批身份、并发重建和 HTTP 连接边界。

建议围绕四个可验证的不变量整改：异步任务持有稳定归属；只有有效代次可提交或派发；持久成功后才发布成功；未知状态不得授权破坏性操作。共享机制只在确有共同生命周期时抽取，避免制造一个过大的通用框架。

对应回归应覆盖 Git 查询失败、定时器准点与分片、删除后迟到完成、落盘失败、迁移第二步失败、生成中切项目、引擎切换恢复、spawn 过程中取消、重复停止、审批过户取消、目标设置/清除交错、DNS 检查与连接解析不一致。不要只测正常路径。

审查中还验证了一个被排除的怀疑：在独立临时目录创建含 65MB 文件的沙盒，再原样应用回源，结果 skippedFiles=1、deletedFiles=0，源大文件仍存在。因此没有把“导入跳过大文件导致直接误删”列为发现。临时目录已清理。
